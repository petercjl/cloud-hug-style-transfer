# SealSeek 媒体执行

本 Skill 负责产品卡、页面方案、参考选择、PSD 图片位、授权范围与业务验收。`@petercjl/sealseek-media-cli` 及其规范 `sealseek-media` Skill 负责认证、实时模型能力、参考传输、提交、任务恢复、下载和画板写入。沿用上游 v0.5.2 的分工，不直接调用未经声明的 HTTP 接口。

## 依赖与当前入口

业务任务先核验必需媒体依赖。优先使用宿主已发现的 `sealseek-media`，读取其实际目录中的入口与规范来源。调用它的 `skill source --json`，核对逻辑名和拥有包身份；完整读取返回的当前 `SKILL.md` 和适用宿主适配，后续相对路径从该规范目录解析。宿主支持 Node.js 22+、命令执行、文件访问和实际看图；身份不能只由一个同名命令证明。

本包附带上游原有依赖核验函数及只读入口：

```text
node <SKILL_ROOT>/scripts/check-media.mjs --package-root <VERIFIED_SEALSEEK_PACKAGE_ROOT>
```

`--package-root` 是当前宿主已核验的媒体包根目录，不是 Skill 目录。未指定时沿用上游 `CLOUD_HUG_MEDIA_ROOT`、npm 和 PATH 发现逻辑。只在本次进程传绑定，不修改系统全局配置。结果的 `invocation.command` 与 `invocation.args` 是经过包身份核验的媒体入口；后续加上媒体当前合同要求的宿主绑定。

缺包、低于 0.6.1、CLI／规范 Skill 不可用或必要能力不兼容时暂停业务流程，保留输入，给出具体诊断及最短恢复方式；不要自行替换提供商。纯 Skill 审阅／更新不运行生图服务。依赖修复是否安装或更改环境，遵守当前用户授权，原样本包不含凭据、不内嵌旧媒体包。

本版本已合入 `@petercjl/cloud-hug-style-transfer`。业务任务先通过当前 Skill 的 `scripts/run.mjs doctor --json` 核验包与媒体依赖；维护时不加载生成服务。核对 `dependencies.media.ok` 与 `automaticUpdate`，若更新回执要求重载，先重新定位并加载当前规范 Skill。上面的 `check-media.mjs` 是只读媒体核验辅助入口，不能替代所属包的安装、更新和完整性检查；包管理使用同一 `scripts/run.mjs` 与当前命令合同，见 [维护说明](maintenance.md)。

## 一轮发现，按需重查

按媒体包当前主线获取实时能力、认证与模型目录；参数准备时查询选定模型。不要把本地版本通过当作已登录、有额度或服务可用。诊断失败才按当前合同使用 `doctor --live --json` 等入口，成功结果在同一版本／账户／能力条件下复用。检测到包或规范 Skill 更新后重新定位并加载，不盲目复用旧参数。

模型由媒体包当前默认值或用户明确选择决定。用户没点名模型时通常不传 `--model`，不能为了图中文字、速度或效果自动换模型。读取当下分辨率、比例、参考数量、传输合同及限制；不支持本轮要求时报告具体限制，请用户作必要选择。

## 每次生成的输入职责

| 阶段 | 需要实际传入的依据 |
| --- | --- |
| 产品设定卡 | 按 [产品规则](products.md) 从整套资料为本款色选出的互补整体／细节参考；有多个有效视角必须实际传入，只有单一视角时记录限制。需要时附仅约束形式的拼版样例；不用人物卡 |
| 单图素材 | 最终确认产品卡＋对应模板／摄影图片位＋必要品牌正例；有人物时附当前模特卡 |
| 三图／四宫格的独立图片位 | 对应方向与格位的完整计划＋涉及的确认产品卡＋该格模板依据；需要人物才附模特卡 |
| 完整无字页面 | 对应整页模板＋本方向所有格位计划＋涉及产品卡；有人物时附模特卡 |

模板旧动物和旧人物不能覆盖产品卡与人物卡。生成说明写清每张参考的职责和不迁移内容。按实际参考上限先删重复氛围图，保护产品、人物和模板约束；不能仅列文件路径却没有真正传图，也不默认拼接所有参考。多个颜色的素材只传对应颜色及本图确需出现的其他确认颜色，避免混色。

提交前核对实际请求中的有序参考与准备清单一致，特别检查产品卡是否遗漏已选的其他有效视角。参考清单必须对应真实传入的图片，不把仅供 Agent 浏览的图片算作模型输入。原图与裁图的来源关系、每张的约束职责和冲突处理结论留在项目记录中。

## 授权阶段与提交

用户明确进行品牌升级后可按本流程生成产品卡；产品卡生成授权不延伸到详情图。详情图必须经过产品与需求确认、整套规划、方案及生成范围确认。只确认卡片时不能开始首屏试跑。

每个输出单独提交一张，先用当前合同的 `--dry-run --json` 检查，支持的模型参数通过后才执行。在本轮画板绑定下使用 `--canvas ID --archive none --via sealseek --submit`（准确参数仍以当前媒体 CLI 为准）。画板先验证再生成，具体见 [归档](canvas-comparison.md)。

请求中包含目标格位／模式、无字要求、完整本案摄影安排与有序真实参考。不要把 A/B/C 当作同一提示词随机跑三遍；不同方向必须发送各自完整计划及规划中的关键区别。保存实际提交的完整提示词、参考顺序与来源／职责、非敏感生成参数、任务 ID 和输出文件对应关系，便于核对“计划了什么”和“实际提交了什么”；不记录认证凭据，记录无需展示在用户问答中。等待单次不超过 60 秒，任务进行时持续简短报告有效进展。

## 恢复与验收

按当前 `task get/wait/resume/diagnose/download` 合同处理同一任务。提交结果未知、超时或中断，先检查保存的任务 ID 与远端状态；不创建新 ID 重提、不悄悄额外收费。下载失败只恢复下载；归档失败保留已有图片，按同一画板、同一元素 ID 恢复，不为了保存重新生成。

自动跟踪和允许的恢复继续执行；模型明确失败或需新付费生成时按实际授权处理。不要把用户对原计划的认可无限扩大为反复试模或额外方案。

成功状态后验证本地文件存在、可打开、实际尺寸与数量，实际看图评估产品、人物、构图、无字和品牌质量。产品卡须按 [产品原图对照](products.md) 检查已知外观、卡内视角及同形态配色间的结构；详情页须按 [三案对照验收](planning.md) 检查 A/B/C 的计划差异。规则检查、dry-run、单张看验和用户确认都不能代替这两项对照。交付模型、文件、真实画板和仍存在的问题，不宣称未测试的生成效果。
